# Loop Engineering — Addy Osmani

Google 엔지니어 [[wiki/entities/people/addy-osmani|Addy Osmani]]가 쓴 "Loop engineering"을 정리한 글(GeekNews/하다 클립). AI 코딩 에이전트의 다음 단계로, 사람이 매번 직접 지시하는 방식에서 벗어나 **에이전트가 일을 찾고·나누고·검증하고·다음 작업을 정하는 반복 시스템**을 설계하는 관점을 다룬다.

## 요약

기존 코딩 에이전트 사용은 "개발자가 프롬프트 작성 → 결과 확인 → 재지시"의 수동 루프였다. 루프 엔지니어링은 이 과정을 **자동화된 구조**로 바꾼다. 즉, 사람이 매번 지시하는 대신 "무엇을 찾고, 어떻게 처리하고, 언제 멈출지"를 시스템으로 설계한다. 다만 글은 이를 만능 해법으로 보지 않고 토큰 비용·검증 책임·이해도 저하라는 현실 비용을 함께 강조한다.

## 핵심 포인트

### 루프의 구성 요소
- **자동 실행** — 정해진 목표를 향해 반복 실행되는 작업 흐름
- **워크트리(worktree)** — 같은 저장소를 여러 작업 공간으로 분리해 충돌 감소 (Git 기능)
- **스킬(skills)** — 프로젝트 규칙·지식을 문서화해 에이전트가 매번 추측하지 않게 함
- **플러그인 / 커넥터** — Linear·Slack·DB 등 외부 도구와 연결하는 통로
- **서브에이전트** — 작업을 분담하는 별도 에이전트들
- **외부 메모리** — 대화 밖에 상태를 남겨 다음 실행이 이어받게 함

### 장점
- **반복 업무 절감** — CI 실패 요약, 이슈 분류, 최근 커밋 검토 자동화
- **병렬 처리** — 여러 에이전트가 각자 다른 워크트리에서 작업해 파일 충돌 감소
- **지식 재사용** — 프로젝트 관행·빌드 절차를 스킬로 보존, 매 세션 같은 설명 반복 불필요

### 단점과 위험
- **검증 부담은 사라지지 않는다** — 루프 결과는 여전히 사람이 확인해야 함
- **토큰 비용 증가** — 서브에이전트가 늘면 각자 모델·도구를 별도 사용
- **이해도 부채** — 결과를 읽지 않고 받아들이면 코드베이스는 커지지만 사람이 이해하는 범위는 줄어듦

### 차별점 — 프롬프트 엔지니어링과의 구분
- 프롬프트 엔지니어링: "한 번의 좋은 질문"에 초점
- 루프 엔지니어링: "반복 가능한 작업 시스템" 설계에 초점
- Codex와 [[wiki/entities/tools/claude-fable5|Claude Code]]가 자동화·스킬·MCP 연결·서브에이전트 등 유사 구성 요소를 갖추면서, 도구 자체보다 **루프 설계**가 더 중요한 관심사로 부상

### 특장점 — 설계의 핵심
- **작성자와 검증자의 분리** — 코드를 만든 에이전트가 스스로 평가하면 관대해지므로, 별도 서브에이전트가 검토하는 구조를 제안
- **외부 메모리 유지** — 마크다운 파일·이슈 보드처럼 대화 밖 상태를 남겨야 다음 실행 때 이어받을 수 있음
