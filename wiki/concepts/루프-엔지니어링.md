# 루프 엔지니어링 (Loop Engineering)

AI 코딩 에이전트를 사람이 매번 직접 지시하는 방식에서 벗어나, **에이전트가 일을 찾고·나누고·검증하고·다음 작업을 정하는 반복 시스템**으로 설계하는 접근. Addy Osmani가 제시한 개념.

## 프롬프트 엔지니어링과의 차이

| 구분 | 프롬프트 엔지니어링 | 루프 엔지니어링 |
|------|--------------------|------------------|
| 초점 | 한 번의 좋은 질문 | 반복 가능한 작업 시스템 |
| 사람 역할 | 매번 지시·결과 확인·재지시 | 루프 구조·검증 조건·기록 방식 설계 |
| 단위 | 단발성 요청 | 자동 실행되는 작업 흐름 |

## 구성 요소

- **자동 실행** — 목표를 향해 여러 번 반복 실행되는 작업 흐름
- **워크트리** — 같은 저장소를 여러 작업 공간으로 분리해 충돌 감소 (Git)
- **스킬** — 프로젝트 규칙·지식을 문서화해 에이전트가 추측하지 않게 함
- **커넥터/플러그인** — Linear·Slack·DB 등 외부 도구 연결
- **서브에이전트** — 작업 분담, 특히 **작성자와 검증자 분리**
- **외부 메모리** — 대화 밖(마크다운·이슈 보드)에 상태를 남겨 다음 실행이 이어받음

## 두 가지 설계 원칙

1. **작성자와 검증자의 분리** — 코드를 만든 에이전트가 스스로 평가하면 관대해진다. 별도 서브에이전트가 검토해야 함.
2. **외부 메모리 유지** — 대화는 휘발한다. 상태를 대화 밖에 남겨야 루프가 이어진다.

## 장점과 비용

- **장점**: 반복 업무 절감, 병렬 처리(워크트리), 지식 재사용(스킬)
- **비용**: 검증 부담은 사라지지 않음 / 토큰 비용 증가 / **이해도 부채**(읽지 않고 수용하면 코드는 커지나 이해 범위는 축소)

> 좋은 루프가 좋은 판단을 대신하지는 않는다. 코드를 읽고 검증하고 한계를 이해하는 엔지니어링 역량이 없으면 자동화는 속도보다 위험을 먼저 키운다.

## 이 브레인과의 대응

이 세컨드 브레인 자체가 루프 엔지니어링의 구현체다.

| 루프 요소 | 이 저장소의 구현 |
|-----------|------------------|
| 스킬 | `CLAUDE.md`, brain-workflow 스킬 |
| 외부 메모리 | `wiki/`, `index.md`, `log.md` |
| 서브에이전트(분업) | brain-ingest(Sonnet) / brain-clip·lint(Haiku) |
| 작성자–검증자 분리 | ingest(작성) ↔ lint(검증) |
